4. Código completo corregido
No hay errores que corregir, así que mantengo la estructura original. Solo añado las
mejoras mínimas que considero razonables (validación del callback), sin reescribir nada:
function aplicarOperacion(a, b, funcionOperacion) {
 if (typeof funcionOperacion !== 'function') {
  throw new TypeError('El tercer argumento debe ser una función');
 }
 return funcionOperacion(a, b);
}
function sumar(a, b) {
 return a + b;
}
function restar(a, b) {
 return a - b;
}
function elevarA(a, b) {
 return a ** b;
}
console.log(aplicarOperacion(5, 3, sumar));
console.log(aplicarOperacion(5, 3, restar));
console.log(aplicarOperacion(5, 3, elevarA));
console.log(aplicarOperacion(5, 3, (a, b) => a * b));

Si necesitas compatibilidad con navegadores antiguos (IE11), cambia a ** b por
Math.pow(a, b).
5. Buenas prácticas y mejoras opcionales
Validar el callback (ya añadido). Evita fallos confusos.
Validar los operandos si esperas números:
if (typeof a !== 'number' || typeof b !== 'number') {
    throw new TypeError('a y b deben ser números');
}
Útil si los datos vienen de un formulario o de una API.
Nombres: funcionOperacion es correcto pero largo. En código real se suele llamar
callback, operacion o fn. Es cuestión de estilo.
Math.pow vs **: usa ** si el entorno lo soporta (recomendado hoy). Math.pow solo si
necesitas compatibilidad muy antigua.
Comentarios JSDoc: en una función que recibe un callback, ayuda documentar el
contrato:
 * @param {number} a
 * @param {number} b
 * @param {(x:number, y:number) => number} funcionOperacion
 * @returns {number}
Coherencia: si defines sumar, restar y elevarA como funciones nombradas, quizá tenga
sentido definir también multiplicar en lugar de una arrow inline. Es solo estética.
Resumen final: el código es correcto. Solo he añadido una validación defensiva. Ningún
